# ADR 0001. Технические решения по API

- **Статус:** принято
- **Дата:** 2026-11-07
- **Задача:** [#1 «Зафиксировать технические решения по API»](https://github.com/trkpo/goals_app_backend/issues/1)
- **Связанные документы:** [`docs/API.md`](../API.md), [`api/openapi.yaml`](../../api/openapi.yaml)

## Контекст

`docs/API.md` описывает поведение эндпоинтов, но оставляет открытыми транспортные детали: формат
ошибки, передачу версии записи, точную семантику реакций, поведение фильтра ленты и способ
подтверждения удаления. Без этих решений нельзя писать ни backend, ни клиент: обе стороны должны
одинаково понимать `409 VERSION_CONFLICT`, `Idempotency-Key` и курсор.

Ниже решения, которые становятся обязательными для backend и frontend. Они уже учтены в
`api/openapi.yaml`; расхождений с `docs/API.md` нет — документ дополняется приложением.

## 1. Единый конверт ошибки

Все ответы с ошибкой — `application/json` и один объект:

```json
{ "code": "TITLE_LENGTH", "message": "Заголовок должен быть от 3 до 100 символов", "field": "title", "request_id": "7f3c2a1e-..." }
```

- `code` — стабильный машинный идентификатор из перечня `ErrorCode` в OpenAPI. Не переводится и не
  меняется при правках текста; клиент ветвится только по нему (например, `field` для подсветки поля).
- `message` — готовый текст для пользователя на русском языке. Для `5xx` — общее сообщение без
  деталей (NF_Err_1); трассировки, SQL и имена сервисов в ответ не попадают.
- `field` — JSON-путь поля запроса (`"title"`, `"reflection.fact_text"`), `null`, если ошибка не
  привязана к полю (F_Common_4). Валидация формы показывает `message` рядом с этим полем.
- `request_id` — значение заголовка `X-Request-Id`. Сервер принимает входящий заголовок или
  генерирует UUID и всегда возвращает его в ответе; по нему ищут запись в логах.

Соответствие кодов и статусов: `400` — синтаксическая/неподдерживаемая конструкция запроса
(`INVALID_SORT`, `INVALID_RESULT`, `INVALID_CURSOR`, `CONFIRM_REQUIRED`), `401` — нет или истёк
доступ, `403` — действие запрещено, `404` — объект не найден, `409` — конфликт состояния
(`EMAIL_TAKEN`, `VERSION_CONFLICT`, `GOAL_LOCKED`, `ALREADY_PUBLISHED`, …), `410` — истёк срок
(`RESET_TOKEN_EXPIRED`), `422` — ошибка валидации поля (`REQUIRED_FIELD`, `TITLE_LENGTH`,
`INVALID_SCORE`, …), `429` — частота (`Retry-After`), `500` / `503` — внутренняя ошибка и
недоступность. Один код всегда отдаётся с одним статусом.

**Почему не `application/problem+json` (RFC 9457).** Клиенту нужен `field` для привязки ошибки к
полю формы, а `problem+json` не описывает его без расширения. Конверт уже используется в
сгенерированном клиенте (`fieldError`), менять его дороже, чем задокументировать.

## 2. Версия записи и конфликты

Версия записи передаётся HTTP-заголовком `ETag`, а не полем в теле:

- `GET /goals/{goal_id}` и `GET /profiles/me` возвращают `ETag: "<version>"` — сильный валидатор.
  `PATCH` этих ресурсов возвращает новый `ETag` вместе с телом.
- Клиент при изменении передаёт `If-Match` с последним полученным `ETag`. Сервер сравнивает версию
  и пишет изменение **в одной транзакции**, поэтому параллельная правка не может «проскочить».
- Несовпадение → `409 VERSION_CONFLICT`. Ответ дополнительно содержит актуальный `ETag`, чтобы
  клиент мог показать конфликт и перечитать данные без лишнего запроса.
- Заголовок не передан → изменение выполняется без проверки версии (последняя запись побеждает).
  Это допустимо только для автосохранения черновика (F_Goal_13), когда клиент ещё не успел получить
  `ETag`; остальные экраны обязаны передавать `If-Match`.
- `ETag` не дублируется полем в JSON: одно представление ресурса — один набор полей. Списки
  (`goals.list`, `feed.list`) `ETag` не отдают.
- Версия увеличивается при каждом изменении записи: профиль, цель, признак видимости публикации,
  смена статуса и сохранение итога — всегда вместе с записью в одной транзакции (NF_Data_2).

**Почему `If-Match`, а не поле `version` в теле.** Механизм стандартный (RFC 9110), не требует менять
схемы тел, работает и для `PATCH`, и для `DELETE`, и позволяет кэшировать ответы. Поле в теле пришлось
бы добавлять в каждую схему и проверять вручную.

## 3. Семантика реакций

- Модель: одна реакция пользователя на публикацию — уникальная пара `(publication_id, user_id)` с
  типом `support | energy`. Двух реакций одновременно быть не может (F_Feed_6).
- `PUT /feed/publications/{publication_id}/reactions` — идемпотентная установка. Если реакции нет —
  создаётся; если стоит другой тип — заменяется; если тот же тип — **снимается** (F_Feed_7). Ответ
  всегда `200` с актуальными `my_reaction`, `reactions` и `reactions_total`; при снятии
  `my_reaction: null`. Ошибки `400 INVALID_REACTION`, `403 CANNOT_REACT_TO_OWN`, `404 NOT_FOUND`.
- `DELETE /feed/publications/{publication_id}/reactions` — безусловное снятие, идемпотентное: `204` и
  тогда, когда реакции не было. Повторный вызов безопасен.
- Счётчики хранятся по типам (`support`, `energy`); `reactions_total` — их сумма, отдельно не
  хранится, поэтому не может разойтись с типами. Популярность ленты считается по этой сумме
  (F_Feed_2) и попадает в окно «самые популярные».
- `my_reaction` заполняется только при валидном access-токене; для анонимного читателя — `null`
  (лента доступна без входа, F_Feed_1).
- Изменение реакции, счётчиков и признака версии публикации — одна транзакция; карточку ленты
  обновляет задание проекции.

## 4. Фильтр `result` в ленте и курсор

- `result` — **пост-фильтр к уже полученной странице**, как и записано в `docs/API.md`: сначала
  выбирается страница по курсору и сортировке, затем из неё убираются публикации с другим типом
  итога. Поэтому страница может быть короче `limit` и даже пустой при непустом `next_cursor`
  (F_Feed_9).
- `next_cursor` считается по последней строке **исходной** страницы, а не по последней оставшейся
  после фильтра. Он возвращается всегда, когда исходная страница была полной; клиент не должен
  останавливать подгрузку на пустой странице.
- Фильтр не входит в ключ курсора: при смене `result` клиент начинает с начала (курсор без фильтра).
- Сортировки: `popular` читается из заранее посчитанного окна по сумме реакций; `newest` и `oldest` —
  из одной таблицы порядка в двух направлениях. Ключ сортировки всегда дополняется `publication_id`,
  поэтому вставки не дают дублей и пропусков внутри просмотра.

**Почему не фильтр в SQL с курсором по отфильтрованному набору.** Это потребовало бы отдельного
индекса и отдельного курсора под каждый тип итога, а поведение «страница короче `limit`» уже
зафиксировано в контракте. Пост-фильтр дешевле и не меняет контракт.

## 5. Подтверждение удаления

- `DELETE /goals/{goal_id}` и `DELETE /profiles/me` принимают тело `{ "confirm": true }` — так
  записано в `docs/API.md` (F_Goal_7, F_Prof_6).
- Отсутствие тела, `confirm: false` или иное значение → `400 CONFIRM_REQUIRED`. Это не ошибка
  валидации поля, поэтому не `422`.
- `Content-Type: application/json` обязателен. `DELETE /feed/publications/{publication_id}` тела не
  требует: скрытие и повторная публикация выполняются через `visibility`.

**Почему тело, а не query.** RFC 9110 не запрещает тело у `DELETE` — семантика определяется
описанием метода в API; клиент у нас один (SPA), а Caddy на стендах проксирует запрос как есть, без
срезания тела. Тело оставляет место для расширения подтверждения (например, причины удаления) без
изменения URL и кэша. Если появится клиент, который не умеет тело у `DELETE`, вопрос пересмотрим.

## 6. Пагинация

- Курсор — непрозрачная строка `base64url` от ключа сортировки и `id` последней строки; клиент его
  не разбирает и не конструирует.
- `limit` — целое `1..100`, по умолчанию `20`. `next_cursor: null` — страниц больше нет.
- Повреждённый или чужой курсор → `400 INVALID_CURSOR` (добавлен в `ErrorCode`).
- Курсор привязан к сортировке: при смене `sort` клиент начинает с начала. Фильтр `result` в курсор
  не входит (см. п. 4).

## 7. Идемпотентность

- `Idempotency-Key` — строка `1..255` символов, область действия — пользователь + метод + путь.
- Ключ и результат (статус и тело ответа) хранятся 24 часа. Повтор с тем же ключом возвращает
  сохранённый ответ, вторая запись не создаётся и побочные эффекты не повторяются.
- Тот же ключ с другим телом → `409 IDEMPOTENCY_CONFLICT` (код добавлен в `ErrorCode`).
- Без ключа: повторное создание → `409` (`EMAIL_TAKEN`, `ALREADY_PUBLISHED`), повторное удаление →
  `404`, повторное чтение → `200`. `PATCH` идемпотентен по значению полей.
- `GET` и `DELETE` с телом `confirm` ключ не требуют, но принимают.

## 8. Что меняется в контракте

- `docs/API.md`: добавлено приложение «Технические решения», уточнены пагинация и `VERSION_CONFLICT`.
- `api/openapi.yaml`: в `ErrorCode` добавлены `INVALID_CURSOR` и `IDEMPOTENCY_CONFLICT`; `If-Match`
  описан как необязательный с явной семантикой; `ETag` отдаётся на чтение и изменение цели.
- Backend: фильтр `X-Request-Id`, перечень `ErrorCode`, единый обработчик исключений, поддержка
  `ETag`/`If-Match` и `Idempotency-Key` — в задачах #6 и #8.
- Frontend: ошибка привязывается к полю через `fieldError` (уже есть в `api/client`).

## Последствия

Плюсы: у backend и frontend один источник истины, конфликты правок воспроизводимы, повторные запросы
безопасны. Минусы: пост-фильтр ленты может отдавать короткие страницы — клиент обязан это учитывать;
подтверждение удаления телом требует `Content-Type` и корректной работы прокси.
